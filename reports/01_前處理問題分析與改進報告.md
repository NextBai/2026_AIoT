# 物聯網音檔前處理問題分析與改進建議報告

本報告針對已刪除的舊前處理資料夾（原 `白噪音3秒音檔`）進行詳細的聲學檢測數據紀錄、問題診斷與改進方針說明。

---

## 一、 背景與資料集總覽

- **原音檔目錄**：`物聯網音檔/`
- **說話者數量**：4 人（吳、甯、白、蕭）
- **朗讀文本**：每人朗讀 3 首古詩，共 12 條錄音：
  1. 《黃鶴樓送孟浩然之廣陵》（故人西辭黃鶴樓，煙花三月下揚州…）
  2. 《江雪》（千山鳥飛絕，萬徑人蹤滅…）
  3. 《相思》（紅豆生南國，春來發幾枝…）
- **原音檔特徵**：
  - 格式：AAC-LC 編碼（`.m4a` 容器）
  - 取樣率：`48,000 Hz`
  - 聲道：表面為 2 聲道 Stereo，經檢驗左右聲道波形相關係數為 `1.0000`（完全相同之 **Dual-Mono** 偽雙聲道）
  - 錄音時長：`7.06s ~ 12.69s`，說話者語速、停頓與開頭結尾靜音（0.5s~1.3s）差異大。

---

## 二、 舊前處理方式逆向工程還原

舊前處理資料夾（`白噪音3秒音檔`）採用了以下處理邏輯：
1. **降取樣與轉格式**：由 48kHz Stereo 轉為 `16,000 Hz, 16-bit Mono WAV`（每個檔案固定 48,000 點採樣，體積剛好 96,044 Bytes）。
2. **時間截取機制**：使用**全固定長度居中硬切**：
   $$\text{截取起始點 (offset)} = \frac{\text{原始總樣本數} - 3 \times 16000}{2}$$
3. **注入隨機雜訊**：在截出的 3 秒片段直接疊加隨機白噪音。

## 四、 舊前處理的 7 大致命問題分析

### 1. 矩形窗硬切引發邊界瞬時不連續與點擊爆音（Clicks / Pops / Spectral Leakage）
- **機制**：截取 3 秒音訊時，未進行**平滑加窗（如 Hann/Hamming 窗）**、未做**淡入淡出（Fade-in / Fade-out）**，亦未尋找零交越點（Zero-crossing）。
- **實證**：`甯1_noise.wav` 的第 0 點起始振幅高達 **+0.3063**，`吳1_noise.wav` 為 **-0.1676**，`吳2_noise.wav` 結尾振幅斷在 **+0.1805**。
- **後果**：波形從 0 瞬間躍升至 0.3 會形成階躍響應（Step discontinuity），在時頻分析（FFT / Mel-Spectrogram / MFCC）的第一幀與最後一幀產生**無限頻寬的高頻爆音脈衝線**。機器學習模型極易學習到這個人工切音的假特徵，而非真正的聲紋特徵。

### 2. 居中硬切腰斬語素與共振峰（Phonetic Fragmentation）
- **機制**：直接從音檔中間硬切 3 秒，完全不考慮人類說話的字詞與句子邊界。
- **後果**：例如 吳1「煙花三月下揚州」，「煙」字被生生切斷，只剩下後半部分發音；蕭3「願君多採擷」的「擷」字被硬切一半。共振峰過渡軌跡（Formant transitions）與時序脈絡被嚴重破壞，模型無法取得完整的音素聲學特徵。

### 3. 有效訊號嚴重丟棄與樣本極端稀疏（丟棄率 60% ~ 76%）
- **機制**：原檔時長介於 7.06s ～ 12.69s，每檔卻僅單次截取 3 秒，其餘訊號全部拋棄。
- **實證**：蕭1（12.69s）被拋棄了高達 **76.4%** 的有效語音。
- **後果**：
  - 聲紋識別與語音分類模型最忌諱資料量過少。
  - 原本只有 12 條錄音，切完後**依然只有 12 條 3 秒音檔**（每位說話者僅 3 條樣本）。這對於訓練 ECAPA-TDNN、ResNet34、X-vector 等現代深度學習模型來說，樣本數極端匱乏，勢必引發嚴重過擬合或無法收斂。

### 4. 加噪後微弱語音被徹底吞噬（蕭1 ASR 辨識直接歸零）
- **實證**：在加噪後的 Whisper ASR 評估中，`蕭1_noise.wav` 的語音辨識輸出為 **完全空白 `""`**。
- **機制**：蕭1 本身錄音能量偏低（RMS -28.8 dBFS），且切出的 3 秒剛好處於較平緩的停頓與弱發音處，在未經響度補償的情況下疊加白噪音，直接導致訊號落入不可辨識的雜訊區間。

### 5. 訊噪比（SNR）飄移不均勻（波動達 8.5 dB）
- **實證**：
  - `白2` 的真實 SNR 高達 **21.5 dB**（雜訊微弱）。
  - `甯2` 的真實 SNR 卻只有 **13.1 dB**（雜訊十分強烈）。
- **機制**：加噪程式沒有先將音訊正規化，亦未針對每條音檔動態計算目標 SNR，而是以固定幅度加噪，導致不同說話者承受了極不平等的雜訊污染，模型會將「雜訊強度」誤判為「說話者識別特徵」。

### 6. 未實施響度正規化（Loudness Normalization）
- **機制**：原始音檔中，各說話者與麥克風距離、發音力量不同（白3 峰值高達 -1.3 dBFS，蕭3 峰值僅 -8.2 dBFS，RMS 相差 5.0 dB）。
- **後果**：前處理完全未做能量標準化（如 ITU-R BS.1770 或 RMS 標準化），導致音量大小偏差直接傳遞至特徵矩陣中。

### 7. 噪音型態單一且脫離真實物聯網（IoT）邊緣環境
- **機制**：加噪僅使用電腦隨機生成的純高斯白噪音（AWGN）。
- **後果**：在物聯網（IoT）真實部署場景中，麥克風面臨的是 50/60Hz 電源交流蜂鳴聲（Hum）、散熱風扇低頻噪聲（Fan Noise）、室內混響殘響（Reverberation）與非平穩瞬態環境聲。純高斯白噪無法提升模型在真實物聯網場景下的強健度（Robustness）。

## 五、 建議改進前處理標準流程（Recommended Pipeline）

建議重構前處理管線，採用以下標準化處理流程：

```
[原始音檔 48kHz Stereo]
       │
       ▼
1. 聲道精簡 (Mono Conversion)
   - 取左右聲道平均，消除偽雙聲道冗餘
       │
       ▼
2. 高品質抗混疊降取樣 (Anti-aliased Resampling to 16kHz)
   - 採用 Sinc / 多相濾波器降取樣至標準 16,000 Hz
       │
       ▼
3. 語音活動檢測 (VAD)
   - 裁切前後導無效靜音（保留約 100ms 緩衝），僅保留實質語音段
       │
       ▼
4. 響度正規化 (Loudness Normalization)
   - 統一調整至固定目標能量（例如 RMS = -20 dBFS 或 -23 LUFS）
       │
       ▼
5. 滑動窗口資料擴增 (Sliding Window Segmentation)
   - 採用 3.0 秒窗口，50% 重疊（步長 Hop Size = 1.5 秒）
   - 每條 9 秒語音可擴增為 4~6 個樣本，總樣本數擴增至 60~80 條以上！
       │
       ▼
6. 平滑加窗處理 (Smooth Windowing)
   - 在每個切片片頭與片尾加入 10ms ~ 20ms 的平滑淡入淡出（Hann/Tukey 窗），根除階躍爆音
       │
       ▼
7. 精確訊噪比控制與真實環境雜訊擴增 (Controlled SNR Augmentation)
   - 動態計算訊號功率 $P_{\text{signal}}$ 與雜訊功率 $P_{\text{noise}}$
   - 支援隨機指定目標 SNR 區間（如 10dB ~ 25dB）
   - 加入真實物聯網環境噪音庫（風扇聲、辦公室環境聲、混響）
```
